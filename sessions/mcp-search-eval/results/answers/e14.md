# e14 — `searchBySummarization` strategies: performance/cost tradeoffs

## Question

What are the performance/cost tradeoffs between `searchBySummarization: 'page'` vs other summarization strategies in `queryGroup`?

## Answer

The `searchBySummarization` parameter in `queryGroup` has three possible values — unset (default), `page`, and `outline` — each with different performance and cost characteristics.

### Default (unset / `false`) — embeddings-based

When `searchBySummarization` is not configured, Sensible uses an embeddings-based approach:

- Splits the document into equally sized chunks.
- Scores each chunk for relevancy using embeddings.
- Combines the top-scoring chunks as context for the LLM.

**Advantage:** Fast.
**Disadvantage:** Brittle — can struggle when the same concept appears multiple times across the document, making it hard to identify the most relevant passage.

### `searchBySummarization: 'page'` (equivalent to `true`)

Each page of the document is treated as one chunk. Sensible then uses a two-step completion-only RAG strategy:

1. An LLM summarizes each page.
2. A second LLM identifies the most relevant pages from those summaries and uses their full text as context.

**Advantage:** Often outperforms the default approach; particularly useful for long documents with repeated mentions of the same concept (e.g., long legal documents).
**Cost implication:** Requires two LLM calls (one for summarization, one for identification), compared to the single LLM call in the default embeddings approach.

### `searchBySummarization: 'outline'`

Instead of treating each page as a chunk, an LLM first generates a table of contents (outline) of the document. Each segment of that outline becomes a chunk, then the same two-step process applies.

**Difference from `page`:** The chunk boundaries follow the document's logical structure (outline segments) rather than physical page breaks. This can produce more semantically coherent chunks, but requires an additional LLM call to generate the outline first, adding further cost.

### Short-document shortcut (≤5 pages)

When `searchBySummarization` is configured for a document that is **5 pages or fewer**, Sensible bypasses summarization entirely and submits the whole document as context. This removes the extra LLM calls and their cost for short documents.

### Chunk count impact

When `searchBySummarization` is configured for a document **longer than 5 pages**, Sensible automatically sets the Chunk Count parameter to 5 and ignores any manually configured value. For the default (non-summarization) approach, the Chunk Count default is also 5 but can be overridden.

### Summary table

| Strategy | Chunk definition | LLM calls to find context | Accuracy on long docs | Notes |
|---|---|---|---|---|
| Default (embeddings) | Equal-sized text chunks | 0 (uses embeddings scoring) | Can be brittle | Fastest, lowest cost |
| `page` | One page = one chunk | 2 (summarize + identify) | Often better | Recommended for long/complex docs |
| `outline` | Outline segment = one chunk | 2+ (outline generation + summarize + identify) | Potentially best for structured docs | Additional outline-generation step |

## Quality verdict

**4/5**

The docs provide clear, direct information on what each strategy does mechanically, the key short-document shortcut behavior (≤5 pages), and the explicit statement that `page` often outperforms the default and is useful for long documents. The main gap is that the docs do not give concrete cost figures (e.g., token counts, latency numbers, or price comparisons) and do not describe `outline` with the same depth as `page`. There is also no direct comparison between `page` and `outline` in terms of when to prefer one over the other. Still, the functional tradeoffs are documented well enough to make an informed choice.
