# e06 — Computed field cross-references and evaluation order

## Question
Can computed fields reference other computed fields, and if so, is there a declared evaluation order or does it depend on array position?

## Answer

The docs do not directly address whether a computed field can use another computed field's output as its `source_id`. The fetched pages focus on computed fields referencing regular *fields* (not other computed fields) as sources.

What the docs do describe clearly is the **evaluation order** of computed fields relative to other constructs:

### Default evaluation order (`sensiblehq/field-order`)

When `fields`, `computed_fields`, and `sections` are declared as separate sibling arrays (the default syntax), Sensible evaluates them in this fixed sequence:

1. All entries in the `fields` array.
2. All computed fields that are **not** Suppress Output methods.
3. All Suppress Output computed fields.
4. Sections.

Within the computed fields pass, non-suppress computed fields run first as a group, then Suppress Output fields run as a group. The docs do not state that computed fields within the same pass are ordered by array position relative to each other — only that the two categories (non-suppress vs. suppress) are sequenced.

### Configurable evaluation order

An alternative syntax merges everything into a single `fields` array. This lets you control the order explicitly — for example, declaring sections before a computed field that zips them, then a suppressOutput computed field after. The docs give this as the solution when the default order causes a dependency to fail (e.g., a zip computed field returning null because sections hadn't run yet).

### Implication for computed-field-to-computed-field references

The docs do not explicitly confirm or deny that a computed field can reference another computed field by `source_id`. However, the configurable single-array syntax is presented as the mechanism for handling ordering dependencies between any field types. If such cross-references are supported, the configurable syntax would be the correct tool for ensuring the source computed field runs before the referencing one.

**No explicit statement** in the fetched docs confirms that computed fields can take other computed fields as sources.
